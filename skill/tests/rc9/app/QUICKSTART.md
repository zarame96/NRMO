description は147文字（rc8-upload1 と同じ文言）。rc9 では、これが通常の配布パッケージそのもので、別の互換版はない。

## 1. 登録

1. ハッシュを確かめる。一致しなければ登録しない
   - Mac：`shasum -a 256 nrmo.skill`
   - Windows：`certutil -hashfile nrmo.skill SHA256`
2. 既存の nrmo（rc8-upload1 など）をオフにするか削除し、rc9 を登録して、有効な nrmo を1件だけにする。登録に失敗しても、それだけを理由に正常に動いている旧版を削除しない
3. 可能なら、メモリと過去のチャット参照をオフにする。オフにできなければ、オンのまま実施したことを記録する
4. 一覧に表示された版名・説明文を記録する（スクリーンショットかメモ）

## 3. 記録（1回ごと）

- 応答全文

採点は応答全文を受け取ってから行う。記録表は `RECORD.md`。実施報告・本文受領・本文評価・環境確認を別々に記録し、確認できなかった項目は「未確認」と書く。うまくいかなかった回も消さず、やり直しは `A1_r1-retry1` のように別名で残す。

## 4. 見るポイント

rc8 の基準（`../../rc8/PLAN.md`）に加えて、rc9 PLAN（`../PLAN.md`）の期待1〜7。特に：

- A1：相談にない承認・行動履歴を「確定できること」や理由に書いていないか。退職などの回復可能性を一般論で断定していないか
- A2：問い合わせ・見積もりを未確認のまま「無料」「費用0」と書いていないか。状態不明なのに「ACTIVE のまま」と書いていないか。初期費用を二重に数えていないか。初期費用上限と合計損失上限の区別、撤退条件の複数の読みの保留（rc8 で改善した点）が保たれているか
- A3：「21日」を「21日から」「21日時点」「10月21日」などの日付にしていないか。終了を尊重し、確認の質問を強いていないか
- A4：ALB で判定せず、採用ルールの選択を待たずに通常の支援を示すか
- A5：翻訳だけが返るか
